# PostgreSQL company isolation (IAM-002)

This applies to the current organization and identity tables. It adds no HTTP endpoint and does not yet protect future employee, payroll or document tables.

## Current request boundary

The API validates the Keycloak access token and obtains the user ID from that token. Before a company is selected, the membership lookup signs a short-lived subject scope and sets it for its database transaction; PostgreSQL returns only that user's active memberships. The company-context lookup first verifies the user's active membership, then signs both subject and selected company for the company-read transaction. PostgreSQL checks the proof against a key in a private schema before accepting the scope. Commit or rollback clears the transaction-local settings before the pooled connection is reused. The company ID in a URL or query is a requested scope, never proof of access.

All current organization and identity-owned tables have row-level security enabled and forced, including the company-creation and membership audit tables. Normal HTTP uses `olarize_runtime`, which is not a table owner and cannot bypass RLS or assume provisioning/migration roles. The controlled company and identity provisioners have separate, narrowly scoped policies. Membership administration uses its audited database functions and checks current `identity.admin` authority; ordinary runtime SQL cannot write membership rows. Composite foreign keys require a membership audit row's company ID to match the referenced membership's company ID, because foreign-key checks bypass RLS.

**Credential boundary:** `DB_SCOPE_KEY` is a separate 32-byte key encoded as 64 hex characters. The migration stores it in `olarize_private.scope_signing_key`, which the runtime role cannot read; the backend receives it through deployment secrets. The application signs subject, optional company and expiry for each database transaction. A caller with only runtime SQL credentials can set the custom settings but cannot produce a valid proof for another subject or company. Administrative function wrappers check the same proof against the actor and company arguments, and the internal security-definer functions are not executable by the runtime role. PostgreSQL verifies the application proof; Keycloak token validation remains the application's responsibility. Compromise of both the database credential and signing key remains outside this boundary. Keep the two secrets separate, use parameterized SQL, and never log the key or proof.

Set the same `DB_SCOPE_KEY` in the one-off Flyway migration task and every backend replica before applying V6. For local development, add a generated value to the ignored `.env` file (`openssl rand -hex 32` can generate one); the project does not commit this key. Do not change it on an existing database without a planned key-rotation migration and coordinated backend rollout. A missing or mismatched key denies protected reads. The database protects its private key table with schema/table grants rather than company RLS because it contains one deployment-wide technical secret, not company data.

## Extending the contract to another company table

Before exposing a new company-owned table, add `company_id` to every row and index it for scoped lookups. Add a Flyway migration that enables and **forces** RLS, grants the runtime only the operations the feature needs, and defines SELECT and write policies against the transaction-local company and verified subject or a narrower current permission. Deny missing context. For a reference to another company-owned row, enforce matching company IDs with a composite key and foreign key; a policy alone cannot secure foreign-key checks. Use a dedicated audited provisioning path only if the feature needs one, and do not give its role to the HTTP runtime.

The application service must derive subject from the validated token, verify current membership and permission, then sign and set the context inside the same transaction as the SQL. A background job must establish an explicitly verified service scope before touching company data; no subject means no default company access. Keep PostgreSQL integration tests using the real restricted role for missing or forged context, two-company reads/joins/counts, INSERT/UPDATE checks, revocation, transaction commit/rollback reuse, cross-company references and administrator-function impersonation. Ordinary new persistence should use JPA entities, repositories and mappers; the current JDBC company lookup is retained for setting PostgreSQL-specific RLS context on the exact read transaction.

For a visible local check, start the stack as described in [development](development.md), sign in to Swagger as the synthetic `olarize-demo-admin` account, then call `GET /api/v1/identity/memberships` and `GET /api/v1/identity/company-context`. Both return the persisted Demo Morocco SARL seed. These routes have not changed shape; IAM-002 constrains what PostgreSQL can return. `./scripts/verify-backend.sh` runs the direct restricted-role isolation checks.
