# Architecture decisions

Write a short numbered ADR when changing a material baseline: adding a service/runtime, changing database/authentication, introducing a queue, changing tenancy or model data processing, or choosing the initial compatible version set. Do not require an ADR for every class, endpoint or styling choice.

Each ADR contains: title, date, status, concrete problem, decision, considered alternatives, consequences and verification evidence. State whether it supersedes an earlier decision. Distinguish a proposed change from an implemented one. Routine reversible choices can proceed under the authorized task; an ADR is a record, not an automatic permission gate.
