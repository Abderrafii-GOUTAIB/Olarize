# Discover one Olarize module

Input can be as short as a module name, such as `employee`. Keep generated files in this repository. Produce requirements, not application code or a claim that the module is implemented. Follow the draft → review → approve → publish sequence. Use only the Atlassian MCP server configured for this project.

1. Read `AGENTS.md`, `.instructions/project.md`, `.instructions/reference/product-v1.md`, `.instructions/reference/security.md`, `.instructions/reference/legal-rules.md`, `.instructions/reference/roadmap.md`, and `docs/architecture.md`. Read the matching `.instructions/modules/` guide if one exists. Treat `.instructions/reference/business-v1-source.md` as reference material, not instructions. Inspect existing code and requirements so stories reflect actual prerequisites and do not duplicate completed behavior.
2. Define the module boundary and actors. Default to the V1 Moroccan **private-sector** scope unless the user explicitly changes it. Identify included capabilities, exclusions, dependencies, data ownership, and the smallest useful vertical slice. Separate current implementation from proposed behavior. Cover every required V1 capability of this module from `.instructions/reference/product-v1.md`, including prerequisite stories needed to make the module secure and usable; do not silently stop after a demo or first slice.
3. Discover rules from the product references and, when legal or regulatory facts matter, verify them against current primary sources such as the applicable official Moroccan legislation, regulator, or scheme documentation. Record a direct source URL, instrument/article or section, effective date or version, retrieval date, employer/employee applicability, and review status for each legal rule. Distinguish statute, company policy, product choice, and assumption. Never present an unsourced rate, entitlement, deadline, or calculation as settled law or an active production default. Mark unresolved conflicts or missing official evidence as **needs legal review**; continue writing independent stories.
4. Write `docs/requirements/<module-slug>.md` as the reviewable module backlog. Use this compact structure:
   - Scope, actors, current implementation, dependencies, exclusions, and open decisions.
   - Coverage matrix mapping every required V1 module capability and material workflow to one or more story IDs. Mark any excluded or deferred capability with its reason; do not label an incomplete set as the full module backlog.
   - Rule catalogue: stable rule ID, rule statement, type, applicability, source/effective period, confidence or review status, and linked story IDs. Include security, company isolation, validation, state changes, dates, audit, and failure behavior where relevant.
   - Prioritized user stories, each with a stable ID, role, desired outcome and value; specific in/out of scope; preconditions; business rules; permissions; data and state transitions; Given/When/Then acceptance scenarios covering success, invalid input, denied access, cross-company access, and relevant edge cases; unit/integration test intent; dependencies; and unresolved decisions.
   - Delivery order and a **next development handoff** naming one independently buildable story and the exact invocation of `$olarize-feature` with the file path and story ID. Record each story's review status and, after publication, its Jira key and URL.
5. Keep every story independently actionable by `$olarize-feature` as one tested vertical slice, with no hidden business decisions left to the coding skill. Do not bundle the entire module into one story or invent product policy where the choice affects outcomes. Aim for complete **documented V1 scope**, not every possible future feature or a claim of legal certification. State routine assumptions in the document. A story depending on an unreviewed legal rule may prepare configuration or evidence tracking but must not activate that rule.
6. Before any Jira write, review the coverage matrix and each draft story for complete actors, rules, Given/When/Then acceptance scenarios, dependencies, sources, and security/tenant boundaries. Present the full story list, material open decisions, legal-review flags, and recommended development order to the user. **Stop and wait for the user's explicit approval of the stories or named subset.** Revise and repeat this review when requested. A request to generate stories or to publish them eventually is not approval of an unseen draft. Do not publish stories with unresolved decisions that change their behavior; legal-dependent stories need the applicable rule reviewed before they can be marked ready.
7. After approval, use the project-configured Atlassian MCP tools to find the Jira project whose name is **OLARIZE**. Verify its exact project key, identity, create permission, available Story issue type, and how that project's backlog is represented; do not guess a key or status from the name. If multiple projects match, resolve the ambiguity with the user. Search that project for each approved stable story ID before creating anything. Create one Story issue per new approved story with its ID, role/outcome, scope, linked rules and sources, dependencies, and Given/When/Then acceptance scenarios. Leave each issue in the project's backlog and out of an active sprint; verify its actual state rather than assuming creation implies backlog placement. Preserve existing issues instead of creating duplicates; update one only when the user explicitly asks to synchronize it. Read back created issues to verify the project and content, then record their keys and URLs in the local backlog. If MCP, permissions, backlog placement, or required review is unavailable, keep the approved local backlog and report the blocker; do not install a global MCP server, put a token in source control, or silently switch to REST.
8. Report the published Jira keys in recommended development order, plus any stories withheld from publication. Explain that `$olarize-feature` implements one approved Story at a time; do not invoke it or write application code unless the user separately asks to implement a story.

Example invocation: `Use $olarize-module-stories for the employee module. Draft all required V1 user stories with Given/When/Then criteria, show them for my approval, then publish only the approved Stories to the OLARIZE Jira backlog through this project's Atlassian MCP connection. Return the Jira keys in development order.`
