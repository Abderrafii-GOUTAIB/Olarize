WHY SOME OF THIS FELT CONFUSING

Important distinctions in your actual setup.

The developer agent is not your future HR assistant.

Codex helps write software. modules/assistant.md describes the future assistant inside Olarize. modules/knowledge.md describes future product RAG. You do not need either product feature to use a coding agent.

The reviewer configuration and dashboard use different launch paths.

In Codex, the named olarize-reviewer.toml role can define a reviewer session. The current dashboard service starts a separate read-only Codex CLI session with the review skill instead; it does not directly select that TOML role. Nested subagents are disabled in those CLI sessions. The coordinator handles the sequence.

A subagent appearing in this conversation is temporary.

A separate reviewer was asked to inspect the development tool. It is a delegated AI session, not an extra backend service, permanent employee, or new application module. It can use the same AI model as the main agent.

Some documents describe the long-term product, not today’s work.

The original roadmap promotes early AI and AWS staging. Your later choices govern the current scope: backend-only features for now and a managed Moroccan hosting target, with the provider still to be selected and verified. AWS and RAG guidance do not mean those systems are already deployed or implemented.

The files do not automatically make code clean or scalable.

They guide consistent work. Tests, architecture checks, independent review and your diff review provide evidence. Product scalability still comes from sound data access, module boundaries, background processing and suitable deployment resources.

The connected workbench is implemented, but live integration is not fully verified.

The service and dashboard have local automated checks. Provider authentication, a committed remote develop branch and publication credentials are separate prerequisites. Manual planner progress is never evidence of a real test or deployment.
